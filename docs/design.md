# Anvil 技术设计

## 桌面产品方案（2026-10-30）

### 问题与目标

用户需要在一个 macOS / Windows 桌面工作台中完成提出 coding 任务、查看代码、审阅差异、执行测试和 Git 交付。现有命令行原型验证了执行循环，但没有桌面文件编辑、Git 视图和交互终端。产品只面向 coding，不提供独立 Web 产品、npm CLI 产品、通用办公连接器或动态插件平台。

### 已确定的方案

- Electron + React + TypeScript；界面使用本地打包资源。
- Monaco Editor 负责文件编辑和只读 Diff；xterm.js + node-pty 负责交互终端。
- Harness 放在独立进程，通过类型化 IPC 连接界面；优先验证 OpenCode 2.0 执行内核复用，具体接入门槛见下文。
- Git 使用本机 Git CLI，复用用户已有远端凭据。首次使用检测 Git，缺失时给出指引。
- 后续用 SQLite 保存会话与任务事件；不为第一阶段提前建立空数据库、模型设置或假会话。
- 主进程只负责桌面生命周期和受限操作入口；renderer 开启 context isolation、禁用 Node 集成。终端命令拥有当前用户权限，进程分离不等于沙箱。

### 第一阶段范围

本阶段交付可操作真实仓库的桌面基础闭环：原生目录选择、仓库状态和分支、分层文件浏览、文本文件编辑与保存、工作区 / 暂存区 Diff、交互终端。保留命令行原型作为内部开发入口，不将其作为新产品分发形式。

Git 状态以 porcelain 输出为准。工作区 Diff 比较 index 与文件；暂存区 Diff 比较 HEAD 与 index。未跟踪文件、新增、删除、重命名分别处理；二进制、符号链接、子模块和过大文件明确显示限制。支持尚无首个提交的仓库及含空格、Unicode 的路径。

文件保存先验证读取时的版本，文件被外部修改时拒绝覆盖；切换文件、仓库或关闭窗口时保护未保存编辑。路径必须留在已打开的仓库内，不读取或覆盖符号链接目标。状态刷新保留未保存缓冲区，不把全部仓库差异归因给 agent。

终端绑定当前仓库，切换仓库或退出应用时终止旧 PTY；创建、输入、尺寸和销毁通过受限 IPC。界面刷新清理遗留终端。Git 与文件操作异步执行，Git 输出与文本读取设置大小上限。

### 界面设计

以对话为主的工作台：左侧项目与本地对话草稿，中央对话及输入区始终保留，文件 / Git Changes / 编辑器 / Diff 放在按需打开的右侧审阅面板。终端默认收起且首次打开才启动，收起时保持进程。顶部展示当前项目、分支和审阅入口。

当前尚未接入模型，允许准备并保存本地草稿；发送按钮明确禁用，不制造回复、执行日志或成功状态。草稿与仓库绑定，切换审阅面板不影响输入。右侧关闭只收起视图，保留未保存文件缓冲区；切换文件和退出时仍执行未保存保护。窄窗口保留对话与输入空间，Diff 可使用行内模式。

颜色：工作区 #171b22、侧栏 #1c222c、面板 #242c38、分隔线 #343e4d、正文 #dce4ef、强调 #87b7f5。界面使用系统 UI 字体，代码与终端使用系统等宽字体。用分隔线表达区域，不使用装饰性卡片、渐变或动画。保留清晰键盘焦点、可调整侧栏和终端、空状态和可恢复错误。

### 优先级调整

用户确认核心投入在 harness。桌面只提供执行观察、代码审阅和人工介入所需的基础能力；Git Graph、复杂历史及完整 Git 客户端不阻塞 harness 开发。布局可参考 VS Code 的 Changes / Diff，后续历史图参考 GitKraken、Fork 的信息组织，但不因此扩大当前实现范围。

### Harness 复用策略

优先验证 OpenCode **2.0.0** 作为执行底座，保留 Anvil 自己的 Electron / React 对话 UI。官方 `@opencode/sdk` 提供进程内 host，可以复用会话、模型适配、工具、权限和事件接口；将 host 放进独立执行进程，通过 Anvil IPC 连接界面，不要求用户安装 npm CLI。先验证运行时和打包依赖、会话恢复、取消和权限行为，再替换现有原型；版本与上游修改明确记录。

不同时引入两套 agent loop。DeepSeek 的 Cordis 插件组合不整体迁入，针对上下文派生、工具并发边界、取消和日志等具体机制择优借鉴。采用 OpenCode 自带模型适配时，不重复叠加 pi-ai。自研投入集中在可测量的 coding 行为、上下文与反馈策略，而非重写已有执行基础设施。

依据：[OpenCode 2.0 SDK](https://github.com/anomalyco/opencode/blob/v2.0.0/packages/sdk/README.md)、[DeepSeek agent loop](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.5/packages/core/agent-loop/README.md)。当前是集成方向，尚未将 SDK 接入产品。

2026-10-30 隔离验证：npm 存在 `@opencode/sdk@2.0.0`，对应上游 tag 的提交为 `63f7ceecbed2d7d9a627518d935dd963b9d4ac9f`。在临时目录以 `--ignore-scripts` 安装后，Node 22.22.0 直接导入报 `ERR_MODULE_NOT_FOUND`（SDK 内部无扩展名引用）；加入 tsx 后遇到 server 包的目录导入错误。一次 Node ESM bundle 尝试又暴露 `ffi-rs` 原生模块打包要求。以上是该 npm 产物在本次 Node 路径下的结果，不代表其 Bun 或官方桌面运行时不可用。未调用模型、未读取用户凭据、未添加到 Anvil 产品依赖。

接入选择：先验证上游支持的构建和运行时组合；若 SDK 的 Electron 独立进程封装成本过高，再评估随应用捆绑同版本官方执行程序。两条路径都需通过 macOS / Windows 打包后启动、流式事件、批准/拒绝工具、取消任务、会话恢复测试，再决定正式采用。SDK 的数据库默认在内存，正式接入必须明确持久化路径。保持 MIT 许可证及第三方声明，记录补丁与版本，避免长期维护大范围 fork。

状态：首版最小闭环已实现并通过本地测试；真实模型执行尚未验证，ChatGPT 订阅授权实验暂缓。

## 问题定义

编程 agent 的任务表现不仅取决于模型本身，也取决于仓库上下文的组织方式、可用工具、执行反馈和错误恢复机制。若这些能力与单一模型深度耦合，更换模型就容易要求重写执行逻辑，也难以公平衡量模型与 harness 各自带来的收益。

Anvil 要构建一个专注 coding 的 harness，让模型可以替换，让执行流程可以验证，并通过真实任务评测持续改进。目标是在真实编程任务中超过 Claude，以 Claude Code 作为主要产品对标。该目标需要评测证据支持，不能作为初始版本已实现的结论。

## 解决方案

首版采用单 agent、单任务的执行循环，先验证最小闭环。

| 模块       | 职责                                                                             |
| ---------- | -------------------------------------------------------------------------------- |
| 模型适配层 | 将内部消息与工具定义转换为提供商协议，将响应转换为统一的文本、工具请求和结束状态 |
| 上下文管理 | 记录任务、必要的仓库内容、工具结果和执行历史；控制上下文体积                     |
| 代码工具   | 搜索、读取文件和应用修改；限制修改范围为授权工作目录                             |
| 命令执行   | 运行编程所需的检查与命令，记录退出码、输出和超时状态                             |
| 执行循环   | 调用模型、处理工具请求、反馈执行结果，并执行终止与重试限制                       |
| 结果记录   | 汇总修改、验证结果、耗时、用量及未完成事项                                       |

核心流程：接收任务 → 获取上下文 → 调用模型 → 执行工具 → 反馈结果 → 验证修改 → 完成或有界重试。

模型适配必须明确报告不支持的能力。首版先实现一个适配器，随后用第二个提供商验证边界是否合理，不为尚未出现的需求设计通用插件系统。

## 首版范围

- 面向已有本地代码仓库的一次编程任务。
- 支持搜索、读取、修改代码及执行相关测试。
- 配置明确的调用次数、重试次数和命令超时上限。
- 保留已有用户修改；执行中断或验证失败时清楚报告状态。
- 使用凭据注入方式接入模型，仓库、日志和任务记录中不保存密钥。
- 默认不自动提交、推送、部署或执行破坏性 Git 操作。

首版不包含通用办公、多 agent 编排、桌面 UI、账号计费或云端任务调度。

## 关键取舍与风险

- **先验证执行闭环**：优先处理工具反馈与验证质量；复杂 UI 和编排会增加早期调试成本。
- **保留提供商差异**：统一核心协议，但不假设所有模型都支持相同的工具调用和上下文能力。
- **限制自动重试**：避免错误循环持续消耗费用或重复破坏代码。
- **区分执行边界与安全沙箱**：工作目录限制无法隔离任意 shell 命令；首版不能宣称具备安全沙箱。具体命令权限与审批机制须在实现前明确。
- **防止误判成功**：工具运行成功或代码发生修改不等于任务完成，结果必须对应任务验收条件。

## 验证与验收

1. 在测试仓库中完成一个小型 bug 修复，目标测试通过，修改范围符合任务要求。
2. 模拟命令失败、工具错误和模型调用中断，确认状态可追踪，且达到限制后停止。
3. 使用第二个模型提供商执行相同类型任务，核心执行循环无需按提供商重写。
4. 检查最终报告能对应实际 diff、执行命令和验证结果，未验证事项明确列出。

后续与 Claude Code 比较时，固定任务集、起始代码、运行环境、权限和预算，记录双方版本、模型与配置。记录任务成功率、耗时、费用及人工干预次数，并重复运行以观察波动；可行时增加相同模型的对照，区分 harness 与模型本身的影响。

## 首版实现决策

- 入口：Node.js 22 命令行，沿用当前 ESM JavaScript，不引入前端、云服务或新构建工具。搜索使用 ripgrep。
- 模型：先接 OpenAI Responses API Key。用户显式指定模型；密钥通过 keygrant 注入。保留普通消息、工具调用和工具结果的内部协议，提供商状态由适配器保存。
- 工具：列出文件、搜索文本、读文件、精确替换、新建文件与运行命令。文件工具拒绝越界与符号链接；精确替换前必须读取文件，并确认读取后内容没有变化。
- 权限：读操作直接执行；每次修改和模型提出的命令由终端交互确认，非交互环境默认拒绝。用户通过 `--check` 指定的验收命令视为已授权，可重复执行。
- 验证：模型给出最终回答后，执行用户指定的验收命令；失败结果回传给模型继续修复。没有验收命令时返回 `unverified`，不能宣称已验证成功。
- 上限：限制模型轮数、每轮工具调用数、上下文字符数、文件大小、命令输出和执行时长。错误交给模型修正时也受同一轮数上限约束，不自动重试 API 失败。
- 凭据：子进程仅继承基本运行环境，不继承模型密钥；API 错误不打印原始响应。首版不持久化对话或工具输出。
- 边界：这是本地执行器，不是沙箱。批准的命令可以访问当前用户可访问的系统资源；文件路径检查无法约束 shell 命令，也不能隔离并行写入的全部竞态。

## 本轮验收

在临时目录中创建一个带失败测试的小项目，用脚本化模型返回驱动真实文件工具与命令执行，验证失败反馈后能够修复并通过测试。同时测试批准拒绝、路径越界、符号链接、读取后文件变化、命令超时、轮数耗尽和 API 历史回传。

脚本化模型只证明执行流程正确，不证明真实模型的编程能力。第二个真实提供商、真实模型端到端测试与 Claude 对照评测仍待完成。
