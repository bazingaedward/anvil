# Anvil 初始设计

状态：初始方案，尚未实现。

## 问题定义

编程 agent 的任务表现不仅取决于模型本身，也取决于仓库上下文的组织方式、可用工具、执行反馈和错误恢复机制。若这些能力与单一模型深度耦合，更换模型就容易要求重写执行逻辑，也难以公平衡量模型与 harness 各自带来的收益。

Anvil 要构建一个专注 coding 的 harness，让模型可以替换，让执行流程可以验证，并通过真实任务评测持续改进。超过 Claude Code 是长期目标，需要评测证据支持，不能作为初始版本已实现的结论。

## 解决方案

首版采用单 agent、单任务的执行循环，先验证最小闭环。

| 模块 | 职责 |
| --- | --- |
| 模型适配层 | 将内部消息与工具定义转换为提供商协议，将响应转换为统一的文本、工具请求和结束状态 |
| 上下文管理 | 记录任务、必要的仓库内容、工具结果和执行历史；控制上下文体积 |
| 代码工具 | 搜索、读取文件和应用修改；限制修改范围为授权工作目录 |
| 命令执行 | 运行编程所需的检查与命令，记录退出码、输出和超时状态 |
| 执行循环 | 调用模型、处理工具请求、反馈执行结果，并执行终止与重试限制 |
| 结果记录 | 汇总修改、验证结果、耗时、用量及未完成事项 |

核心流程：接收任务 → 获取上下文 → 调用模型 → 执行工具 → 反馈结果 → 验证修改 → 完成或有界重试。

模型适配必须明确报告不支持的能力。首版先实现一个适配器，随后用第二个提供商验证边界是否合理，不为尚未出现的需求设计通用插件系统。

## 首版范围

- 面向已有本地代码仓库的一次编程任务。
- 支持搜索、读取、修改代码及执行相关测试。
- 配置明确的调用次数、重试次数和命令超时上限。
- 保留已有用户修改；执行中断或验证失败时清楚报告状态。
- 使用凭据注入方式接入模型，仓库、日志和任务记录中不保存密钥。
- 默认不自动提交、推送、部署或执行破坏性 Git 操作。

首版不包含通用办公、多 agent 编排、桌面 UI、账号计费或云端任务调度。

## 关键取舍与风险

- **先验证执行闭环**：优先处理工具反馈与验证质量；复杂 UI 和编排会增加早期调试成本。
- **保留提供商差异**：统一核心协议，但不假设所有模型都支持相同的工具调用和上下文能力。
- **限制自动重试**：避免错误循环持续消耗费用或重复破坏代码。
- **区分执行边界与安全沙箱**：工作目录限制无法隔离任意 shell 命令；首版不能宣称具备安全沙箱。具体命令权限与审批机制须在实现前明确。
- **防止误判成功**：工具运行成功或代码发生修改不等于任务完成，结果必须对应任务验收条件。

## 验证与验收

1. 在测试仓库中完成一个小型 bug 修复，目标测试通过，修改范围符合任务要求。
2. 模拟命令失败、工具错误和模型调用中断，确认状态可追踪，且达到限制后停止。
3. 使用第二个模型提供商执行相同类型任务，核心执行循环无需按提供商重写。
4. 检查最终报告能对应实际 diff、执行命令和验证结果，未验证事项明确列出。

后续与 Claude Code 比较时，固定任务集、起始代码、运行环境、权限和预算，记录双方版本、模型与配置。记录任务成功率、耗时、费用及人工干预次数，并重复运行以观察波动；可行时增加相同模型的对照，区分 harness 与模型本身的影响。
